## 1. 目标与非目标

### 目标

让 AFM 能把远程服务器上的目录当作「本地目录一样的地方」来浏览和管理，
复用导航器已有的多标签、地址栏、目录树、面包屑、分屏、排序、视图切换等能力。

### 非目标

**永久不做**

- **远程 shell**（SSH exec）。本需求的 SSH 指 **SFTP 文件传输**，不是登录远程机器执行命令。
- **WebDAV / SMB / S3**。SMB 在 Windows 上有原生支持；S3 与 WebDAV 留给后续协议。
- **在远程目录里「新建空文件」**。SFTP 没有 `CREATE`，FTP 的 `STOR` 需要先有本地文件，
  强行实现会得到一个行为不可预期的功能。2026-10-17 用户确认**后续也不必添加**。
- **远程文件的全局搜索**。现有 `global_search` 索引的是本地盘，接远程需要另一套索引策略，
  与本需求正交。

**首版不做，但已排入后续阶段**（即不是「永不做」，是「不在首版」）

- **双向检查差异 / 文件夹镜像 / 双向同步**。见 §8.3 的拆分理由。
- **远程缩略图与预览**。阶段 8，理由见 §8。
- **跨边界传输的批量预检** —— 首版**已经**做「目标同名必须确认」（§5），
  但不做更重的预检：传输前估算总大小、检查可用空间、一次性列出所有会冲突的文件。
  那些列入阶段 6 的传输队列化。

## 2. 关键前提：现有代码已经为此铺了路

这一节是本设计可行性的根据，全部来自仓库代码核实，不是推测。

### 2.1 已有自定义 scheme 与虚拟路径机制

`src/utils/virtual-path-constants.ts` 已经定义了 `sfm://locations`，
`src/utils/virtual-locations.ts` 的 `resolveDirectoryContents()` 会**先判断虚拟路径、
再回落到 `invoke('read_dir')`**。`Locations`（系统位置）与 `WSL` 两个虚拟目录就是这样实现的。

远程位置沿用同一套机制，路径方案定为：

```
sfm://remote/<connectionId>/<remotePath>
例：sfm://remote/c-7f3a/uploads/2026/
```

`connectionId` 是稳定的短标识，指向凭据存储里的连接记录；`remotePath` 是服务器上的路径。

### 2.2 列目录只有一个收口点

`resolveDirectoryContents()` 被以下全部入口复用，**没有旁路**：

- `stores/storage/workspaces.ts`（标签页加载）
- `modules/navigator/composables/use-file-tree.ts`（目录树）
- `modules/navigator/components/file-browser/use-file-browser-navigation.ts`（主导航）
- `modules/navigator/components/file-browser/address-bar.vue`（面包屑同级目录）
- `modules/navigator/components/file-browser/address-bar-editor-dialog.vue`（地址编辑器）

这意味着**加一个 provider 分支，远程目录就能自动获得上面全部能力**，而不是逐个入口去改。

### 2.3 已有动作门禁的统一收口

`src/utils/entry-action-policy.ts` 现在有三个策略：`virtual-location` / `system-mount-root` / `normal`，
用两张 `Set<ContextMenuAction>` 表来禁用动作。远程路径加一个 `remote` 策略是自然的第四种。

### 2.4 项目惯例是内嵌而非扩展

MCP、LAN 分享、批量重命名、默认文件管理器、终端、归档 —— 全部在主线内实现。
唯一的扩展 `kizemo.focus-sync` 是跨产品（要同步到别的软件的对话框），性质不同。

而且：**扩展 API 里不存在虚拟文件系统挂载点**（`packages/api/index.d.ts` 的
`sigma.fs.*` 全部只认本地路径，`ExtensionPermission` 也没有网络出口类别）。
所以「做成扩展」并不能真正避开核心改动，只是把改动挪到更曲折的地方，
还要额外重写一整套 iframe 界面。详见 §7 形态对比。

## 3. 架构

### 3.1 总体分层

```
┌─────────────────────────────────────────────────────────────┐
│  Vue 前端（导航器 UI，不感知 FTP/SFTP 存在）                  │
│  resolveDirectoryContents ←── provider 分发                   │
│  entry-action-policy      ←── remote 策略门禁                 │
└────────────────────────────┬────────────────────────────────┘
                             │ Tauri invoke
┌────────────────────────────┴────────────────────────────────┐
│  Rust 远程层 src-tauri/src/remote/                           │
│  ├─ paths.rs       sfm://remote 路径解析/构造/父级/显示名      │
│  ├─ credentials.rs 连接元数据 + DPAPI 机密存储                 │
│  ├─ connection.rs  连接池（按 connectionId 复用）             │
│  ├─ provider.rs    RemoteBackend trait + 注册表               │
│  ├─ transfer.rs    传输任务、队列、进度、续传                  │
│  ├─ ftp/backend.rs FTP / FTPS 实现                           │
│  └─ sftp/backend.rs SFTP 实现                                │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 路径解析与归一化（新增）

在 `virtual-path-constants.ts` 增补：

- `isRemotePath(path)` —— 是否远程
- `parseRemotePath(path)` → `{ connectionId, remotePath } | null`
- `buildRemotePath(connectionId, remotePath)` → `sfm://remote/...`
- `getRemoteParentPath(path)` → 远程父目录；到根时返回 `sfm://remote/<id>`

在 `virtual-locations.ts` 的三个函数（`resolveDirectoryContents` / `resolveDirEntry` /
`getNavigableParentPath`）加远程分支，与现有 Locations 分支并列。

**注意**：`normalize-path.ts` 里的 `canonicalizePath` / `getParentPath` 对 `sfm://` 前缀的
行为必须显式测试，不能假设。远程路径**不做本地风格的盘符补全、不做 `..` 越出服务器根的钳制**
（服务器根由协议决定，`..` 越过根应当原样交给服务器处理并把错误映射成可读提示）。

### 3.3 后端 trait

```rust
// provider.rs —— 刻意保持小，只放「元数据 + 写操作」
// 传输不在这里，走 transfer.rs，避免 trait 被传输需求撑大
pub trait RemoteBackend: Send + Sync {
    fn list(&self, path: &str) -> BoxFuture<'_, Result<Vec<RemoteEntry>, RemoteError>>;
    fn stat(&self, path: &str) -> BoxFuture<'_, Result<RemoteEntry, RemoteError>>;
    fn mkdir(&self, path: &str) -> BoxFuture<'_, Result<(), RemoteError>>;
    fn rename(&self, from: &str, to: &str) -> BoxFuture<'_, Result<(), RemoteError>>;
    fn remove(&self, path: &str) -> BoxFuture<'_, Result<(), RemoteError>>;
}
```

> ⚠️ **`cargo test --lib` 红线（AGENTS.md 已记录，本设计必须遵守）**
> 被测试链接到的代码**不得触碰 `tauri::AppHandle` 或 `tauri::async_runtime::*`**。
> 否则 `GlobalRuntime<Wry>` 会单态化出 `<Wry as Runtime>`，把 tao 拖进测试二进制，
> tao 里的 `comctl32.dll!TaskDialogIndirect` 需要 comctl32 v6 而测试二进制没有 manifest
> → 加载期以 `STATUS_ENTRYPOINT_NOT_FOUND` (0xC0000139) 崩掉，一个测试都跑不了，
> **且报错里完全看不出跟本模块有关**。
>
> 落地方式：沿用项目既有模式（`dir_reader.rs` / `global_search.rs` 的 `*_blocking` 同步内核
> + 调用方选执行器）。trait 的每个方法都要有对应的同步内核入口，
> 单测只跑同步内核，不引入任何 tauri 类型。

### 3.4 连接池

按 `connectionId` 复用连接。规则：

- 列目录、stat 等元数据操作**复用**已有连接，不每次重连
- 连接空闲超时自动断开（可配，默认 5 分钟）
- 传输期间连接**独占**，不与元数据操作争用
- 断线后不自动重放写操作（见 §6）

### 3.5 凭据存储

| 内容 | 存放 | 保护方式 |
|---|---|---|
| 连接元数据（协议、主机、端口、用户名、初始目录、编码、被动/主动） | `user-data/remote-connections.json` | 明文（不含机密） |
| 密码 | `remote-credentials.json` | **Windows DPAPI** 加密后 base64 |
| SSH 私钥 | **只存路径**，不存内容 | 由用户自己控制文件 ACL |
| SSH 主机公钥（known_hosts） | `user-data/remote-known-hosts.json` | 明文，首次连接需用户确认指纹 |
| 代理元数据（类型、主机、端口） | `user-data/remote-connections.json` | 明文（不含机密） |
| 代理认证信息 | `remote-credentials.json` | **Windows DPAPI** 加密后 base64 |

> 代理全局默认值另存一份在 `user-settings.json` 的 `remote.proxy.default` 下，
> 供「新建连接」时预填。**注意**：`user-settings.json` 是明文落盘的，
> 那里**只放代理地址，不放代理密码**。

> 目录与命名沿用 `%APPDATA%\com.sigma-file-manager.app\` 的既有布局，
> 与 `mcp-access.json`（MCP 令牌）并列。**受保护常量不得改动**：
> mDNS 服务名、legacy 数据目录名、Tauri `identifier` 都不动。

### 3.6 传输层与代理（2026-10-17 用户确认要做）

**核心设计决定：自建一个传输层抽象放在连接之下，不依赖任何 FTP / SFTP 库
是否自带代理支持。传输层内部按「有没有现成轮子」分别处理（见下表）。**

```
┌────────────────────────────────────────────┐
│  ftp/backend.rs   sftp/backend.rs           │  协议层：只管 FTP / SFTP 报文
├────────────────────────────────────────────┤
│  transport.rs                                 │  传输层：「给我一个已连上的字节流」
│  ├─ Direct        TCP 直连         【自写】  │
│  ├─ Socks5        RFC 1928 + RFC 1929 + BIND │
│  │                └→ 委托 fast-socks5        │
│  └─ HttpConnect   CONNECT 隧道     【自写】  │
├────────────────────────────────────────────┤
│  tokio TCP socket                             │
└────────────────────────────────────────────┘
```

**传输层抽象仍然自建，但里面不再重复造轮子（2026-10-17 复核修正）：**

初稿这里写的是「SOCKS5 与 HTTP CONNECT 都自己实现」，理由是「实现量在几百行量级」。
用户提出「尽量复用现有开源项目」后重新核实了全部候选 SOCKS5 crate，
结论要修正 —— **SOCKS5 有成熟的 MIT 轮子，不该自己写**：

| 候选 crate | 版本 | 许可证 | 结论 |
|---|---|---|---|
| **`fast-socks5`** | v1.0.0（2026-09-12 构建，docs.rs 确认） | **MIT**（anyip.io 维护，代理服务商，商业维护中） | **采用**。client + server 双模块；IPv4 / IPv6 / Domain 三种 `ATYP`；No-Auth 与 Username/Password 两种认证；`Socks5Stream` 已实现 `AsyncRead + AsyncWrite`，**可直接喂给 `russh-sftp` 与 `suppaftp`**；依赖仅 anyhow / async-trait / log / socket2 / thiserror / tokio / tokio-stream，**无系统依赖、无 `unsafe`** |
| `socks5-rs` | v2.0.0（2026-06） | MIT | 只做服务端，README 明确「BIND is intentionally not implemented」。**不可用**，我们需要 BIND |
| `tokio-socks` | v0.5.3（2026-05-29） | — | 偏服务端，客户端能力弱于上者 |
| `async-socks5` | v0.6.0（2024-02） | — | 停更 |
| `socks5-async` | v0.1.4（2020） | — | 停更 |

**`Socks5Command` 枚举已核实含 `TCPConnect` / `TCPBind` / `UDPAssociate`** ——
`TCPBind` 正是 FTP 被动模式数据通道所必需的那个（见下），这是选定它的决定性理由。

**HTTP CONNECT 仍自写**：协议只有「发一行请求 + 读完整响应头 + 判状态行 200」，
约一百行；`hyper` 系的 `CONNECT` 支持要引入完整 HTTP 客户端栈，
比手写更重且不更好控。**不引入新依赖。**

**为什么传输层抽象仍要自建（即使内部有轮子）：**

1. **解耦协议选型**。写成自有传输层后，§10 无论最终选哪个 FTP/SFTP 库，
   代理能力都**已经在那里**，不必因为「这个库不支持代理」而换库。
   这是 §10.2 的第 1 条硬约束：`suppaftp` **完全不支持代理**。
2. **同一种「造轮子」，造错层次也是浪费**。真正被复用三次的是**抽象**（Direct / SOCKS5 / CONNECT 三种
   出口对上层看起来一模一样），不是 RFC 1928 的报文编解码。
   把报文交给库、把**选择哪种出口**留给自己，才是正确切分。
3. **减少依赖面**。AFM 是 GPL-3.0-or-later，每引入一个第三方 crate 都要核许可证；
   本次引入的 `fast-socks5` 已逐项核实为 MIT。

**协议要点**（实现时必须覆盖，逐条对应 RFC）：

| 项 | 要求 |
|---|---|
| SOCKS5 协商 | `05 nmethods methods...`，支持 `00` 无认证与 `02` 用户名密码（RFC 1929） |
| 域名交给代理解析 | `ATYP=0x03`（域名），**不要**在本地做 DNS —— 本地 DNS 会泄漏访问意图，也让很多内网部署失败 |
| SOCKS5 BIND | `CMD=0x02`。FTP 被动模式必须用它（见下） |
| 失败响应 | `REP` 字段必须映射成可读文案，不能只报「代理连接失败」 |
| HTTP CONNECT | `CONNECT host:port HTTP/1.1` + `Host:` 头 + 可选 `Proxy-Authorization: Basic` |
| CONNECT 成功判定 | 必须读完整响应头，且**状态行必须是 200**；不能只判断「收到了响应」 |

**FTP 的数据通道是这里最难的部分，必须提前说清楚：**

FTP 有两条通道 —— 控制连接（21）与数据连接。被代理挡住时：

- **SOCKS5 + FTP**：走 **BIND**。客户端请代理在本地开一个监听端口，
  把该端口通过 `PORT` / `EPRT` 告诉服务器，**由服务器反向连回代理**，代理再转发给客户端。
  这是唯一在远程代理场景下正确的做法。
- **HTTP CONNECT + FTP**：**HTTP 代理没有 BIND**。技术上无法干净支持远程代理下的被动模式。
  可行的只有「代理与客户端同网段时，改写 `PASV` 返回的地址为代理地址」这一种本地场景。
  → **决策：HTTP 代理对 SFTP 完整支持；对 FTP 仅支持同网段本地代理，其余情况明确报错并说明原因。**
  不要假装支持，那会在用户最需要它的时候给出静默的错误行为。
- 主动模式（`PORT`）在 NAT 与代理下基本不可用，代理场景下**只支持被动模式**。

**配置形态**：代理是**每连接**配置（不同服务器可能要不同的出口），
同时提供一个全局默认值。代理地址与认证信息同样进凭据存储（DPAPI）。

### 3.7 传输层的可测性

`transport.rs` 刻意做成**不依赖任何协议库**的纯 socket 逻辑，
因此可以在单测里用本地假代理覆盖。**注意：SOCKS5 侧的假服务端不再自己写 ——
`fast-socks5` 自带 server 模块，直接用它当测试夹具**，这也是选它的额外好处
（测试用的假代理与生产用的客户端出自同一份经过审查的实现，不会各写各的）。

需要覆盖：

- 无认证 / 用户名密码两条协商路径
- 域名 vs IP 两种 `ATYP`（且断言**域名没有在本地做 DNS**）
- BIND 是否真的建立并回传正确端口（FTP 数据通道的前提）
- **HTTP CONNECT 的 200 / 非 200 / 连接被拒**（这部分要自己写假服务端，
  因为 HTTP CONNECT 没有现成 MIT 轮子）
- 错误响应 → 文案映射

这让 §3.6 的绝大部分风险**在接 FTP 之前就能被测试吃掉**。

## 5. 门禁矩阵（L2 + 读写全支持 + 跨边界）

`entry-action-policy.ts` 新增 `remote` 策略。远程条目与本地条目混选时，取**最严格**的策略。

| 动作 | 远程条目上 | 远程目录内 | 跨边界（本地 + 远程混选） |
|---|---|---|---|
| 打开 / 进入目录 | ✅ | ✅ | — |
| 新建标签、地址栏跳转、目录树 | ✅ | ✅ | — |
| 新建目录 | ❌ | ✅ | ❌ |
| 新建文件 | ❌ | ❌ | ❌ |
| 重命名 | ✅ | ✅ | ❌ |
| 删除 | ✅ | ✅ | ❌ |
| 下载到本地 / 从本地上传 | ✅ | ✅ | ✅（这是传输，不是文件操作） |
| 复制 / 剪切 / 粘贴 | ✅（远程→远程，阶段 7） | ✅ | ✅（本地↔远程，阶段 7） |
| 拖拽 | ✅（远程→远程，阶段 7） | ✅ | ✅（本地↔远程，阶段 7） |
| 链接 / 快捷方式 | ❌ | ❌ | ❌ |
| 缩略图 / 快速查看 / 打印 | ❌（阶段 8 再开） | ❌ | ❌ |
| 属性 | ✅（只读展示远程元数据） | ✅ | ✅ |

**「复制 / 粘贴」与「拖拽」在跨边界时的语义**（阶段 7 必须写清，否则用户会踩）：

| 来源 | 目标 | 实际行为 | 是否需要中间落地 |
|---|---|---|---|
| 本地 | 远程目录 | 上传 | 否，流式直传 |
| 远程 | 本地目录 | 下载 | 否，流式直传 |
| 远程 A | 远程 B（同连接） | 服务端复制优先，无 `COPY` 指令时退化为「下载再上传」 | 退化路径需要临时落地 |
| 远程 A | 远程 B（跨连接） | 下载再上传，经本地临时目录 | 是 |

> **「剪切 + 粘贴」跨边界必须降级为「复制 + 粘贴」**，且不得删除源。
> 跨网络执行「移动」意味着「传完了才能删源」，中途失败会留下两份，
> 而删除源是本设计里后果最重的操作之一（§6）。首版对跨边界剪切**直接禁用**。

> **目标已存在同名文件**时必须先确认，不得静默覆盖。跨连接路径还要显示
> 「源连接名 → 目标连接名」，否则用户看不出文件被搬到了另一台服务器。

## 6. 破坏性操作与错误处理

删除与重命名是本设计里**后果最重**的操作，与「读写全支持」的决定同时落地。

### 6.1 删除

- **删除远程目录必须递归**，且二次确认对话框要显示**远端完整路径**与**将被删除的条目数**
  （条目数需要先做一次递归统计，可能慢 —— 首版可先只显示路径，统计列入阶段 6）
- 删除**不做回收站**。FTP/SFTP 没有本地那样的回收站语义。
  确认对话框文案必须明确写出「**此操作不可撤销**」
- 删除进行中若断线，**状态是「未知的部分删除」**，必须如实告知，不得显示成成功或失败

### 6.2 断线时不自动重放

传输类的重试是安全的（幂等或可续传）；**写操作不自动重放**。
断线后重试一次 `rename` / `remove` 可能作用在状态已变的对象上。
统一策略：写操作失败即停，把控制权交回用户。

### 6.3 错误分类

`RemoteError` 必须能区分下面几类，因为用户对它们的处置完全不同：

| 类别 | 含义 | 界面处置 |
|---|---|---|
| `Auth` | 认证失败 / 私钥被拒 / known_hosts 不匹配 | 提示重新输入凭据；host key 不匹配要**显式警告** |
| `Unreachable` | 网络不可达 / DNS 失败 / 连接超时 | 提示检查网络与主机名 |
| `Permission` | 有权限但对该路径无权限 | 提示权限不足，可返回上级 |
| `NotFound` | 路径不存在 | 与 Permission 分开（FTP 上两者可能同码） |
| `Protocol` | 服务器拒绝命令、命令不支持 | 明确说明是哪一步失败 |
| `Encoding` | 文件名编码无法解码 | 显示原始字节的替代表示 |
| `Disconnected` | 传输中断 | 传输类给续传；写操作按 §6.2 处理 |

**判死「连接失败」这一个笼统错误** —— 那会让用户无法判断该换密码还是换网络。

### 6.4 文件名编码

很多国内 FTP 服务器是 GBK/GB2312 而不是 UTF-8。连接配置里必须提供**字符编码**选项
（UTF-8 / GBK / Latin-1 / 服务器声明值），并且在无法解码时走 `Encoding` 错误而不是崩溃。

每个阶段都能独立发一个 beta，符合项目「一功能点升一个版本号」的既有做法
（批次 8/9/10 每批各升一个 beta 版本号）。

### 8.1 首版范围（阶段 0–7）

| 阶段 | 内容 | 产出 | 粗估 |
|---|---|---|---|
| **0** | VFS 骨架：provider 抽象 + `sfm://remote` 路径族 + `remote` 门禁 + **假 provider**（不含任何 FTP 代码） | 内核可用，无用户可见功能 | 8–12 |
| **1** | 连接管理 + 凭据存储（DPAPI）+ 设置页 + **传输层 `transport.rs`（直连 / SOCKS5 / HTTP CONNECT / SOCKS5 BIND）** | 可保存连接；代理可用且已单测覆盖 | 9–14 |
| **2** | **FTP 明文** 只读浏览打通导航器 + 下载/上传（简单传输，带进度）+ 代理下的数据通道 BIND | 首个可用 beta | 12–18 |
| **3** | FTP 远程写操作：新建目录 / 重命名 / 删除（含 §6 的安全设计） | | 5–8 |
| **4** | **FTPS** 显式（AUTH TLS）与隐式（990） | | 3–5 |
| **5** | **SFTP**（SSH 私钥 + known_hosts 校验） | 三协议齐备 | 5–8 |
| **6** | 传输队列化：暂停/继续/取消、断点续传、失败重试；删除前递归统计；跨边界批量预检 | | 8–15 |
| **7** | **跨边界拖拽 / 复制粘贴**（含 §5 的语义表与降级规则） | **首版达成** | 6–10 |

首版合计粗估 **约 56–90 人日**（误差可能 ±50%，其中代理相关约 +6–10）。

> 阶段 1 把传输层**提前到 FTP 之前**，是代理这条需求带来的排序变化：
> 传输层不依赖任何协议库，可以先用假代理服务端把 SOCKS5 / CONNECT / BIND 全部测掉，
> 阶段 2 接 FTP 时就只剩「数据通道怎么用 BIND」这一个协议问题。
> 若把代理推迟到 FTP 之后，就要返工修改已经写好的连接层。

### 8.2 为什么跨边界拖拽/复制能进首版，而差异/同步不能

这两件事常被当成一个包，但它们的性质完全不同：

**跨边界拖拽/复制 = 传输队列的 UI 入口。** 数据面在阶段 6 已经建好了，
阶段 7 要做的只是把「拖到远程目录」「复制后粘贴到远程目录」映射到
「上传 / 下载」这两个已经存在的任务类型。粗估 6–10 人日，收益极大
（用户第一次真正能把文件放进远程），风险低。

**差异 / 镜像 / 双向同步 = 一个新产品。** 它要回答的问题传输一个都不回答：

- 差异检测：新增 / 删除 / 修改 / **重命名**四个维度。FTP 的 `MDTM` 通常只有**秒级**精度，
  SFTP 好一些，所以「两边 mtime 相同」不能当作「没变」——必须落到 size + 内容 hash。
- 重命名检测：需要内容 hash + 文件名相似度启发式，且**会误判**（两个不同文件被当成重命名对）。
- 冲突解决：双方都改了同一个文件怎么办？文本可以尝试合并，二进制不能。
  自动覆盖、跳过、还是保留双份 —— 这是**产品决策**不是技术决策。
  批次 7 的教训可以直接套用：「那是安全模型的一部分，不是 UI」。
- 删除传播：镜像同步里「源端删了要不要删目标端」是**最容易造成不可逆损失**的开关。
  配错了就是用户数据的批量消失。
- 首次同步的基线：第一次跑同步以哪边为准？两边都有怎么办？

这些没有一项能靠「传输已经做好了」顺带解决，而且它们叠加在
「FTP 遍历慢 + 编码不统一 + 断线频繁」的底座上做，风险是乘起来而不是加起来。

### 8.3 后续阶段（不进首版，但架构上要提前留口）

| 阶段 | 内容 | 粗估 |
|---|---|---|
| **8** | 远程预览与缩略图（下载到临时目录再渲染） | 5–8 |
| **9** | **纯本地**的双目录差异比较（见下方建议） | 8–12 |
| **10** | 单向文件夹镜像（本地 → 远程，**删除不传播**） | 6–10 |
| **11** | 远程参与差异比较（本地 ↔ 远程） | 8–12 |
| **12** | 双向同步 + 冲突解决界面 | 15–25 |

> ⚠️ **已核实：项目里目前没有任何「比较 / 差异 / 镜像 / 双向同步」的现成能力。**
> `src-tauri/src/lib.rs` 没有对应 command，17 个语言包里也没有一个相关文案键。
> 阶段 9 起是纯新增，没有可复用的地基。

### 8.4 关于「本地左右双屏检查差异」的建议

用户提问：能否顺手做本地双屏的差异检查与同步？

**能做，但建议作为阶段 9 单独发，不要塞进首版。** 理由与拆分方式：

1. **技术上它是三者里最简单的** —— 纯 `std::fs` 遍历，没有网络、没有编码、没有并发写，
   没有断线中断。AFM 已经有左右分屏（批次 9 的 swap-split-panes 就是它），
   「左格 A 目录、右格 B 目录、逐行标出仅在 A / 仅在 B / 两边都有但内容不同」
   在 UI 上是自然延伸。
2. **它本身就是独立可用功能**，不是为远程同步做的垫脚石 ——
   用户确实会比较两个本地文件夹。所以即使远程同步最终不做，这个功能也不浪费。
3. **正确的架构抽象是「比较两个路径」而不是「比较本地和远程」。**
   两端各是一个 `PathSource`，本地与远程各实现一个。这样阶段 9 先用
   `LocalSource × LocalSource` 把差异算法（时间戳精度陷阱、hash、重命名启发式、
   误判处理）在**没有网络不确定性**的环境里调对，阶段 11 只是多接一个
   `RemoteSource`。如果反过来先做远程版，这些算法问题会和网络问题缠在一起调不出来。
4. **双向同步必须最后做**，且删除传播要作为显式开关，默认关。

### 8.5 实施拆分（scope decomposition）

本规格覆盖 13 个阶段，**规模上不允许写成一份实施计划** —— 后续应**逐阶段**
走「计划 → 实施 → 打包验收 → 交接」的循环，每阶段一份计划文档
（沿用 `docs/superpowers/plans/` 的既有约定）。
建议的第一个计划是**阶段 0**；它不含 FTP 代码，风险最低，且是后面所有阶段的地基。

阶段 0–7 之间依赖**严格串行**（阶段 N+1 依赖阶段 N 的抽象），不存在可并行的阶段。
阶段 8–12 与阶段 0–7 **在代码上无冲突**（差异比较不碰 provider trait），
一旦首版发布即可并行启动 —— 这是把它排在首版之后的另一个理由。

## 8A. 分支策略

### 8A.1 结论

**每个阶段一个分支，验收通过即合并到 `main` 并发 beta。**
既不建长期 feature 分支，也不在 `main` 上裸奔。

### 8A.2 为什么不建「全部完成再合并」的长期分支

| 问题 | 说明 |
|---|---|
| 用户拿不到东西 | 首版 50–78 人日 ≈ 2.5–4 人月，期间 `main` 上完全没有远程空间 |
| 分叉越来越难合 | 期间 `main` 还在发版：README、changelog、版本号、i18n 全在动 |
| 发版事故风险 | 批次 11 §9.5 已经踩过「tag 挂到错误提交」的坑。分支越多，`release-publish.mjs github` 越容易对着错的 ref 跑 |
| 阶段 0 白等 | 阶段 0 无用户可见功能，堆在长期分支里毫无意义，但它恰恰是最该先合的地基 |
| 回滚粒度太粗 | 几千行改动一次性进 `main`，出问题难以定位到阶段 |

### 8A.3 为什么不直接在 `main` 上线性推进

项目历史（批次 1–11）确实都是 `main` 线性提交。但那是**单批次规模**下的做法。
单个阶段动辄几千行、跨 Rust + Vue + i18n 三层，一旦要回滚或在真机验收里发现
必须改设计，脏工作区上的回退代价很高。分支是廉价的保险。

### 8A.4 具体做法

```
feat/remote-phase-0-vfs-skeleton      # provider 抽象 + sfm://remote + 门禁
feat/remote-phase-1-connections       # 连接管理 + DPAPI 凭据
feat/remote-phase-2-ftp-browse        # FTP 浏览 + 基础传输
feat/remote-phase-3-ftp-write-ops     # 新建/重命名/删除
feat/remote-phase-4-ftps
feat/remote-phase-5-sftp
feat/remote-phase-6-transfer-queue
feat/remote-phase-7-cross-boundary    # 跨边界拖拽 / 复制粘贴
feat/remote-phase-8-preview
feat/remote-phase-9-local-diff
```

每个分支的标准流程：

1. 从 `main` 切出
2. 写计划文档（`docs/superpowers/plans/YYYY-MM-DD-remote-phase-N-*.md`）
3. 实现 + 单测（阳性对照、注入验证，见 §9.2）
4. 跑全量门禁，与 §9 的基线**逐字对照**
5. `tauri build` 打包
6. 在**打包产物**上跑真机验收清单（`tauri dev` 的界面结论一律作废）
7. 验收通过 → 合并 `main` → 升 beta 版本号 → 发版 → 写 handoff

### 8A.5 工作树

用 `git worktree` 隔离各阶段的工作目录 —— 这套工具链本仓库已在用
（AGENTS.md 记录过 `git worktree add --detach $env:TEMP\afm-baseline-eslint 0f73f159`
做 eslint 基线逐字对照）。隔离后 `main` 随时可以发版，互不干扰。

### 8A.6 发版时的顺序铁律（批次 11 的教训）

**必须先 `git push` 把代码推上去，再跑 `release-publish.mjs github`。**

`gh release create` 会把 tag 建在**当时远端默认分支的 HEAD** 上。
批次 11 先发 release 后推代码，导致 `v3.2.4` 挂着一个指向旧代码的 tag，
资产是新的、代码是旧的 —— 而 `gh release view` 一切正常，只有 `git ls-remote` 才看得出来。

有分支后这条更容易出错：**发版前必须确认当前分支是 `main`，且 tag 指向的是本次提交。**

沿用本仓库既有门禁，逐字对照基线：

| 项 | 基线（HEAD = `aa530414`） |
|---|---|
| `cargo test --lib` | 386 passed |
| `npx vue-tsc --build` | 0 error |
| `npx eslint src` | 179 errors / 0 warnings |
| `npx vitest run` | 186 文件 / 1465 用例 |
| `node scripts/verify-changelog.mjs` | 退出码 0 |

> ⚠️ **eslint 口径必须是 `npx eslint src`**，不是项目脚本 `eslint .`（整仓是 186/121）。
> 混口径会凭空多出 7 个「回归」。单文件 `eslint --fix` 通过 ≠ 回到基线，必须再跑全量对照。

### 9.1 单测

- **路径层**：`sfm://remote` 解析、父级计算、边界情况（根目录、`..`、尾斜杠、中文与空格）
- **门禁层**：§5 矩阵逐格断言，含混选时的最严格取值
- **provider**：用**假 backend** 驱动，覆盖成功/各类错误/断线，**不连真实网络**
- **连接池**：复用、空闲超时、传输独占
- **传输状态机**：暂停/继续/取消/续传/重试的状态迁移
- **前端**：连接表单校验、传输队列 UI 状态、连接管理页

### 9.2 测试纪律（本项目既有教训，必须遵守）

- **阳性对照**：每条断言要证明「新行为确实发生」，不能只测「不报错」。
  同义反复的占位测试（如 `expect(typeof fn).toBe('function')`）一律删掉。
- **注入验证**：至少挑一处判定**故意改坏**，确认对应测试转红；
  还原必须是与注入语义完全无关的独立命令（`snapshot` / `inject` / `restore` 三条显式子命令），
  不要让同一个脚本靠「参数有无」区分两种相反行为。
- **探针要带阳性对照**：判定「某个机制不支持」之前，先确认探针本身能测到已知为真的东西。
- **只断言内存状态的测试抓不到落盘缺陷**：涉及连接配置持久化，
  必须断言真正走一遍存储 `entries()` 的往返。

### 9.3 端到端验收

真机验收**必须用 `tauri build` 的打包产物**（`tauri dev` 下路由页内容区是空白，结论一律作废）。
需要一个本地测试服务器（FTP + SFTP 各一），建议用容器或嵌入式测试服务端起在
`C:\Users\<user>\` 下的普通目录 —— **不要放 `%TEMP%`**，
`global_search/ignore.rs` 的 `builtin_ignored_paths()` 含 `/AppData/Local/Temp`，会被忽略规则剪掉。

| 角色 | 选定 | 许可证 | 关键理由 |
|---|---|---|---|
| Rust FTP | **`suppaftp` 12.2.1** | `MIT OR Apache-2.0` | 2026-10-15 仍在发版；显式+隐式 FTPS、PASV/EPSV/PORT/EPRT、REST 续传、MLSD 结构化解析全覆盖；tokio/smol 双运行时且**有同步接口** |
| Rust SFTP | **`russh` 0.64.1 + `russh-sftp` 3.0.1** | Apache-2.0 | **纯 Rust**，无 libssh2、无系统 OpenSSL → Windows 打包零 C 依赖 |
| 抽象层范式 | **`remotefs`（MIT）的 trait 形状** | MIT | termscp 已用它落地 SCP/SFTP/FTP/S3/SMB/WebDAV，是最贴题的现成范式。**借鉴形状，不必直接依赖** |
| sidecar 兜底 | **`rclone`** | **MIT**（逐字核实） | 冷门协议与疑难连接的兜底，非主路径 |

### 10.2 两条对 §3.6 架构的独立验证

调研独立证实了「自己写传输层」这个决定是对的：

1. **`suppaftp` 完全不支持代理** —— 全 crate 检索 `proxy` 只命中一处讲 NAT 回连的注释，
   没有任何 SOCKS/HTTP 代理实现。**如果依赖库的代理能力，FTP 这条路会直接卡死。**
2. **`russh-sftp` 的 `SftpSession::new<S: AsyncRead + AsyncWrite + Unpin + Send>`**
   只要求「一条异步双向字节流」，**完全不绑定 SSH 实现**。
   我们自己写的 SOCKS5 / HTTP CONNECT 传输层产出的正是这样一条流，可以直接喂进去。

### 10.3 必须写进实现的三个已知风险

| 风险 | 说明 | 应对 |
|---|---|---|
| **`suppaftp` 隐式 FTPS 是 deprecated feature** | `connect_secure_implicit` 被 `#[cfg(all(feature = "secure", feature = "deprecated"))]` 门控 | 接受它，但要**显式开 feature 并加注释说明这是有意使用**，同时在测试里锁住。将来该 feature 消失时能第一时间发现 |
| **`russh` 必须二选一开 TLS 后端** | `aws-lc-rs` 或 `ring`，全关会直接编译失败 | `Cargo.toml` 里显式声明，不要依赖默认值 |
| **示例代码未经编译验证** | 调研侧逐条对照 crates.io 解包源码核实签名，但未执行 `cargo build` | 阶段 1/2 的第一个任务就是把这些示例编译过一遍 |

### 10.4 两个反直觉结论（已被一手来源推翻的常见说法）

- **`rclone` 当前是 MIT，不是 GPLv3 也不是 SSPL。** 仓库根目录 `COPYING` 正文逐字读过（1095 字节 MIT 原文），
  GitHub 识别为 MIT。**网上大量关于 rclone 许可证的说法已过时。**
  建议把该文件快照归档入仓，避免后续会话再次踩这个坑（同样的坑我在本项目的调研简报里也预设错了）。
- **`sshx` 跟 SFTP 无关。** `ekzhang/sshx` 是 Web 端协作终端应用，不是 SSH/SFTP 库，名字撞车容易误选。
- **`ftp` 这个 crate 已死**：最后一次发布 2018-04-15，仓库最后提交 2023-08-04，36 个 open issue。不要因名字直觉就选它。

### 10.5 上游现状（已核实）

上游 `aleksey-hoffman/sigma-file-manager` **已有 `network_shares.rs`**，但只覆盖 **sshfs / nfs / smb**，
**没有 FTP / SFTP / WebDAV 浏览**。FTP 在上游仅以「LAN 分享服务端」形式存在，
且 `remote-file.ts` 的单测明确断言 `isHttpUrl('ftp://...') === false`。

**扩展沙箱只有 `http` 权限 + http/https 主机白名单，没有裸 socket。**
→ 这是「FTP/SFTP 必须实现在 Tauri Rust 侧」的一手依据，**从上游侧再次确认了 §7 的内嵌结论**。
扩展市场 `registry.json` 仅 6 个扩展，全文检索 `ftp|sftp|webdav|remote|ssh` **零命中**。

## 11. 未决问题

1. **多连接同时打开**是否要 —— 连接池已按 id 设计，但 UI 上同时开多个远程标签页的
   体验与内存占用需要实测再定。
2. **差异比较的呈现形态** —— 阶段 9 是复用现有分屏做双格对照，
   还是做一个专门的「比较」视图（像 Beyond Compare）？前者改动小、复用高，
   后者表达力强但要新写一套 UI。建议前者。
3. **删除传播**在镜像/同步里的默认值 —— 本设计建议**默认关**，
   但这是一个产品决策，需要用户明确拍板。配错就是批量数据消失。
4. **远程文件的全局搜索** —— 已移入「永久不做」，若日后要开，需要单独的索引策略设计。
